# WayBlog AI 写作助手设计与任务拆分

## 目标

为后台文章编辑页增加一个基于本地 Ollama 模型的 AI 写作助手，优先满足“先能稳定用”，再逐步补齐更细的写作辅助能力。

核心目标：

- 一键优化标题、slug、正文、摘要
- 正文输出为纯 Markdown
- 自动整理结构，必要时补充小节、列表、标题层级
- 保留原意，不瞎扩写，不新增没有依据的事实
- 给出分类、标签建议
- 支持整体生成建议后分项应用，避免直接覆盖原内容

非目标：

- 不把 AI 设计成 Agent 工作流
- 第一版不做自动创建分类
- 第一版不做自动创建新标签
- 第一版不做局部选中文本改写
- 第一版不做多模型切换和复杂参数面板

## 适用场景

主要面向中文编程文章、开发记录、踩坑总结、教程类内容。

默认风格：

- 专业
- 简洁
- 实战导向
- 少空话
- 保留原意

不建议的风格：

- 夸张营销文风
- 公众号鸡汤风
- 过度学术化表达

## 模型定位

计划接入本地 Ollama 模型 `qwen2.5:1.5b`。

该模型适合：

- 轻度润色
- 结构整理
- Markdown 格式转换
- 短摘要生成
- 分类、标签初步推荐

该模型不适合：

- 长文深度重写
- 专业事实扩写
- 高稳定性的复杂推理
- 多轮复杂工作流

因此产品策略应为：

- 强约束 Prompt
- 轻度润色优先
- 结果先展示，再由用户应用

## 用户体验目标

编辑文章时，用户可以：

- 点击一个大的 `AI 优化` 按钮，一次性拿到整套建议
- 点击字段右侧的小 `AI` 按钮，单独优化标题、slug、正文、摘要、分类、标签
- 在结果面板中预览建议
- 按字段单独应用
- 在确认后点击 `全部应用`

## 交互设计

### 总入口

在文章编辑页增加一个大的 `AI 优化` 按钮。

建议位置：

- 正文编辑区域标题栏右侧
- 或操作区顶部，保证按钮醒目但不压过发布按钮

点击后行为：

- 校验正文是否存在
- 若正文为空，提示“请先填写正文后再使用 AI 优化”
- 调用 AI 接口
- 返回完整建议结果
- 打开结果抽屉

### 单字段入口

以下区域右侧各增加一个小 `AI` 按钮：

- 标题
- slug
- 正文
- 摘要
- 分类
- 标签

行为规则：

- `标题 AI`：基于当前标题和正文生成更合适标题
- `slug AI`：基于标题或正文生成 slug
- `正文 AI`：对当前正文做轻度润色并转 Markdown
- `摘要 AI`：没有摘要则生成，有摘要则优化
- `分类 AI`：结合标题和正文推荐一个现有分类
- `标签 AI`：结合标题和正文推荐若干现有标签，并可附带建议新增标签

### 结果展示

第一版使用右侧抽屉，不使用居中弹窗。

原因：

- 方便与原编辑区并排对照
- 正文建议通常较长，抽屉更适合滚动预览
- 不会完全遮挡编辑器

抽屉内容分区：

- AI 提示与警告
- 标题建议
- slug 建议
- 摘要建议
- 正文建议预览
- 分类建议
- 标签建议
- 底部操作区

每个分区都提供：

- `应用`

底部统一提供：

- `全部应用`
- `关闭`

## 交互规则

### 输入校验

总按钮：

- 正文为空时不调用 AI，直接提示

单字段按钮：

- `标题 AI`：无标题但有正文时允许
- `slug AI`：有标题或正文任一即可
- `正文 AI`：正文为空时提示
- `摘要 AI`：正文为空时提示
- `分类 AI`：正文为空时提示
- `标签 AI`：正文为空时提示

### 覆盖策略

AI 结果默认不直接写回表单。

用户必须：

- 单独点击某一项的 `应用`
- 或点击 `全部应用`

这样可以降低小模型误改内容的风险。

### 新标签策略

第一版只展示“建议新增标签”，不自动创建。

原因：

- 可避免标签泛滥
- 不引入额外标签管理逻辑
- 降低误判造成的脏数据

## 文案与风格规则

### 正文处理策略

固定为“轻度润色 + 自动结构化 Markdown”。

要求：

- 保留原意
- 不新增事实
- 不虚构数据、版本、结论
- 不做大篇幅扩写
- 自动分段
- 需要时补充小节标题
- 有步骤时转为有序列表
- 有并列点时转为无序列表
- 命令、代码、路径使用 Markdown 代码语法

### 默认输出风格

- 语言简洁
- 直接表达结论
- 减少套话
- 面向技术读者
- 适合博客发布

### 标题策略

标题可在不改变原意的前提下优化为：

- 更明确
- 更自然
- 更符合技术博客表达

避免：

- 标题党
- 夸张修辞
- 与正文不符

### 摘要策略

摘要用于文章列表和 SEO 简介。

要求：

- 一到两句话
- 简明概括主题和价值
- 不写空泛评价
- 长度建议控制在 60 到 140 个中文字符

### slug 策略

slug 规则：

- 仅小写字母、数字、连字符
- 尽量短
- 表意清晰
- 基于标题核心含义生成

## 结构策略

第一版采用“自动判断结构”，不强制固定模板。

弱模板规则：

- 教程类优先使用“简介 / 步骤 / 注意点 / 总结”
- 踩坑类优先使用“问题 / 原因 / 解决 / 补充”
- 说明类优先使用“背景 / 做法 / 结果 / 总结”
- 原文已有合理结构时优先保留并微调

后续版本可增加显式模板模式：

- 教程型
- 踩坑记录型
- 原理分析型
- 工具推荐型

## 数据结构设计

AI 优化接口统一返回结构化 JSON，而不是自由文本。

```ts
type AiOptimizeResponse = {
  title: string;
  slug: string;
  excerpt: string;
  content: string;
  categorySuggestion: {
    id?: string;
    name: string;
    reason?: string;
  } | null;
  tagSuggestions: Array<{
    id?: string;
    name: string;
    reason?: string;
    isNew?: boolean;
  }>;
  warnings: string[];
};
```

说明：

- `content` 必须是纯 Markdown
- `categorySuggestion` 优先给已有分类
- `tagSuggestions` 同时支持已有标签和建议新增标签
- `warnings` 用于提醒结果不稳定原因，例如“正文过短”

## 接口设计

### 阶段一最小接口

新增：

- `POST /api/ai/optimize`

请求体：

```json
{
  "title": "string",
  "slug": "string",
  "content": "string",
  "excerpt": "string",
  "categoryId": "string | null",
  "tagIds": ["string"],
  "categories": [{ "id": "1", "name": "Next.js" }],
  "tags": [{ "id": "1", "name": "Prisma" }]
}
```

用途：

- 总按钮
- 单字段按钮也可先复用同一接口

### 阶段二增强接口

可新增：

- `POST /api/ai/field`

请求体示例：

```json
{
  "field": "title",
  "title": "string",
  "content": "string",
  "excerpt": "string"
}
```

用途：

- 针对单字段做更轻量的 Prompt
- 降低单次响应成本

## 服务端设计

建议新增目录：

- `src/lib/ai/client.ts`
- `src/lib/ai/prompts.ts`
- `src/lib/ai/types.ts`
- `src/app/api/ai/optimize/route.ts`

职责划分：

- `client.ts`：封装 Ollama 调用
- `prompts.ts`：维护 system prompt 和任务模板
- `types.ts`：定义请求与返回类型
- `route.ts`：处理鉴权、参数校验、调用 AI、解析结果

### Ollama 调用方式

服务端请求：

- `POST http://127.0.0.1:11434/api/generate`

建议环境变量：

- `OLLAMA_BASE_URL=http://127.0.0.1:11434`
- `OLLAMA_MODEL=qwen2.5:1.5b`
- `OLLAMA_TIMEOUT_MS=60000`

### 返回解析策略

小模型可能不严格输出 JSON，因此需做保护：

- Prompt 中明确要求只输出 JSON
- 服务端尝试提取首个 JSON 对象
- 解析失败时返回明确错误
- 不把模型原始脏输出直接返回给前端

## Prompt 设计

### System Prompt 原则

系统提示词负责定义稳定规则：

- 你是技术博客写作助手
- 你只做轻度润色和结构整理
- 你必须保留原意
- 你不能编造事实
- 正文必须输出纯 Markdown
- 除 JSON 外不得输出其他说明

### Task Prompt 原则

任务提示词负责提供本次输入：

- 当前标题
- 当前 slug
- 当前摘要
- 当前正文
- 当前分类与标签候选
- 输出 JSON 结构要求

### Prompt 关键约束

- 不得新增输入中不存在的事实
- 不要自称模型
- 不要输出解释
- 不要使用代码围栏包裹整个结果
- 分类优先从候选中选择
- 标签优先从候选中选择，最多推荐 5 个
- 建议新增标签最多 2 个

## 分阶段任务拆分

### Phase 1：最小可用版

目标：

- 先做出能正常用的一版
- 优先打通“总按钮 -> AI 返回建议 -> 分项应用”

范围：

- 新增 `POST /api/ai/optimize`
- 接入本地 Ollama
- 增加统一 Prompt
- 编辑页增加 `AI 优化` 大按钮
- 结果抽屉展示：
  - 标题建议
  - slug 建议
  - 摘要建议
  - 正文建议
  - 分类建议
  - 标签建议
- 支持单项应用和全部应用
- 正文为空时提示
- 标签新增建议仅展示，不创建

验收标准：

- 能从后台编辑页发起 AI 优化
- 能拿到结构化结果
- 能把建议应用回表单
- 正文为 Markdown
- 错误场景能给出提示

### Phase 2：字段级优化版

目标：

- 提升交互效率
- 支持按字段单独触发 AI

范围：

- 各字段右侧增加 `AI` 小按钮
- 小按钮可复用总接口，或新增 `POST /api/ai/field`
- 根据字段生成更轻量的 Prompt
- 对摘要为空、slug 为空等场景做更细提示

验收标准：

- 各字段都能独立请求建议
- 不需要每次都生成整套结果

### Phase 3：结果质量增强版

目标：

- 提高分类、标签和正文结构建议质量

范围：

- 引入文章类型弱模板
- 根据内容长度添加警告
- 对 AI 输出做更多格式修正
- 补充“建议新增标签”显示理由
- 摘要长度约束更稳定

验收标准：

- 分类、标签推荐更贴近正文
- 正文结构更稳定
- 异常输出更少

### Phase 4：完善版

目标：

- 让写作助手接近完整产品形态

可选范围：

- 局部选中文本优化
- 模式切换：轻度润色 / 教程化整理 / 踩坑总结整理
- 流式输出
- AI 结果差异对比
- 自动创建建议标签
- 保存 AI 历史记录
- 多模型切换

## 风险与约束

### 模型能力风险

`qwen2.5:1.5b` 可能出现：

- 漏掉部分原文信息
- 输出结构不稳定
- 偶尔擅自补充内容
- JSON 不严格

应对策略：

- 严格 Prompt
- 限制任务只做轻度润色
- 结果先预览再应用
- 服务端做输出解析和兜底

### 性能风险

长文章调用会慢。

应对策略：

- 第一版接受较慢响应
- 设置超时和错误提示
- 后续再考虑字段级调用和流式输出

### 数据一致性风险

AI 推荐分类和标签可能不准确。

应对策略：

- 只给建议，不自动落库新分类
- 新标签先展示，不直接创建
- 分类和标签需要用户确认后应用

## 开发顺序建议

1. 先实现服务端 AI 封装和接口
2. 再实现编辑页总按钮与结果抽屉
3. 再补单项应用逻辑
4. 跑通基础验证
5. 第二阶段再加字段右侧小按钮

## 当前建议的落地范围

优先按 Phase 1 实现。

原因：

- 变更面可控
- 对现有编辑页侵入较小
- 能最快验证本地模型是否够用
- 后续扩展到字段级优化时不用推翻已有结构
